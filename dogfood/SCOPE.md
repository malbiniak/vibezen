- **Session-cost folklore — the idle-resume myth.** (Matt, 2026-07-15, Session 6 — brought in from live project sessions.) Field answer to "is resuming a long, idle session expensive?" The mechanics: "5 minutes" is the prompt-cache TTL, and Claude Code auto-requests the 1-hour TTL on a subscription at no extra cost — you drop back to 5 minutes only past the plan's limit, in paid overage. The timer resets on every message, so the *gap between turns* matters, not how long the session has been alive; an expired cache costs a one-time re-warm of existing context, not an ongoing bleed. *Verified 2026-07-24* against Anthropic's prompt-caching documentation (TTLs are 5 minutes default and 1 hour; the cache lifetime refreshes each time the cached prefix is read) and Claude Code's own runtime documentation (sessions run on the 1-hour TTL; requests drop to the 5-minute TTL in usage overage). One scope note: "no extra cost" holds on a subscription, where there is no metered billing; on the metered API, 1-hour-TTL cache writes bill at 2× base input vs 1.25× for 5-minute. Vendor behavior, not physics — re-check if this entry is acted on long after that date. This confirms Brief 006's diagnosis rather than amending it — the real driver is context bloat, because every turn reprocesses accumulated history. Two things it adds: (a) a §9 tripwire sibling to the attribution trap — fearing idle sessions over a TTL number is the same shape of folk belief, a real mechanic mis-scoped into a cost model; (b) the corollary Brief 006 never states — this is an argument *for* spawning many focused sessions, not against. - **Git model for parallel sessions — same-dir, not worktrees.** (Matt, 2026-07-15, Session 6 — brought in from live project sessions.) Field answer to "worktrees or same-dir for multiple Code sessions on one project?": **same-dir**, and the reasoning is operator-profile-dependent — the generic answer leans worktree, and knowing the operator doesn't read git flips it. A worktree gives each session its own folder *and its own branch*; that isolation bills later as merges, conflicts, rebases, PRs. Three worktree sessions are three diverging copies someone must reconcile; same-dir is one folder, one branch, one history. The real lever is behavior, not the mode: never point two *editing* sessions at the same files — run one at a time, or aim them at disjoint areas (several VS Code windows on one project is already same-dir behavior; just keep them off the same files). Two safety nets replace worktree isolation: **checkpoints** (Code auto-snapshots before every prompt; `/rewind`, or double-Esc on an empty input, undoes Code's changes with no git involved — enough on its own for most non-developers) and **commits** ("commit this" at stopping points = durable restore points, no branch literacy needed). §2 and §4 already imply this (the operator never touches git; "Code does all git work"), but the playbook never says how to run more than one session, and worktrees would smuggle merge literacy onto §4's list. When promoted, a brief settles two things: whether "keep two sessions off the same files" is a Code-side default or the first new item on §4 — a list that claims to be "the whole thing"; and that checkpoints and commits are *file* restart, where Principle 5 is *session* restart. Pairs with the idle-resume entry above.
